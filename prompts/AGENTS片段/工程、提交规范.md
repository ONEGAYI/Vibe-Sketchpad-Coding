## 工程规范

- **文件树维护**：遵循仓库指定的单一数据源和维护入口，不直接修改生成内容。
  - 使用 file-tree 技能的仓库，只通过技能维护入口更新其数据源及生成内容；其他手写文件树不主动同步。
  - 未指定单一数据源时，维护受本次变更影响的已有文件树及其子文档，不额外创建一套文件树。
  - 每次提交前，核对所维护文件树中的相关增删、路径和职责描述是否与实际变更一致。
- **推送与合并**：有远端、具备权限且已获推送授权的仓库，代码变更原则上通过 PR 留痕和审查；只有用户要求合并时才执行合并。
  - 用户验收成果本身不等于授权推送；“跟进 PR 并更改”或明确要求推送、创建 PR，视为授权相应范围内的推送，无需重复确认。
  - 尚未获推送授权时，完成本地修改和验证，交付可供验收的结果；无远端或权限不足时说明限制。
  - **推送前鲜度检查**：推送分支或创建 PR 前先 `git fetch origin` 核对基线分支是否前移（多会话并行仓库的 main 常在中途前移，本地 main 只是建树时的快照）。前移时：未推送分支 rebase 基线、重跑受影响验证后推送；已推送分支（含已建 PR）`git merge origin/<基线>` 进分支解决冲突后正常推送，不改写已发布历史——需要 force-push 的场合仅限用户明确要求。PR 建立后读一次 `mergeable`，非 `MERGEABLE` 不进入等 CI 与合并步骤。
  - **主工作树属于用户**：未经当轮确认，不切换其检出分支、不在其上执行长流程或多代理任务；长期/并行工作一律使用独立 git worktree，主工作树只留给用户本人使用。
  - 外部技能（implement-spec 等）流程内嵌的推送、建 PR、合并步骤不自动构成授权；与推送授权规则冲突时，以本规范为准。
- **项目规则文件维护原则**：新建自有项目时，在根目录同时创建 `AGENTS.md` 和 `CLAUDE.md`；维护既有或他人仓库时遵循其已有约定，不仅为补齐文件而扩大任务范围。以下规则适用于采用双文件约定的项目：
  - `AGENTS.md` 为单一事实源，包含所有 agent 通用规则（行为准则、工程规范、提交规范等）。
  - `CLAUDE.md` 通过 `@AGENTS.md` 导入主文件，仅附加该 agent 专属的补充规则。
  - 修改通用规则只改 `AGENTS.md`；修改专属规则只改 `CLAUDE.md`。
- **报障排查先固定运行路径**：诊断“打不开/跑不起来”类问题时，先确认三件事——用户从哪个目录（工作树）启动、用何种方式（F5 dev 宿主 / vsix / 市场版 / CLI 直跑）、该方式实际加载的产物路径（如 `out/extension.js`、`resource/markdown/dist`、`node_modules`）；三者确认后再深入代码与系统环境，避免在错误的对象上排查。
- **代码编写原则**：对可执行行为的新增或修复，遵循 TDD：先添加或调整验证预期行为的契约测试，确认测试能暴露目标问题，再实现并验证；合理使用烟测和 mock。纯文档、格式等不改变可执行行为的修改，采用内容、格式或渲染检查，不为满足流程添加无意义测试。测试环境受限时，说明未执行的检查及替代验证。

## 提交规范

- （除非要求）用中文编写 spec/plan/CHANGELOG/CLAUDE.md 文档，中文进行提交/PR
- 如果是他人仓库，根据仓库 issue/commit/PR 主流语言确定 issue/commit/PR 的语言
- 提交信息默认使用**中文**；他人仓库遵循上一条语言约定。
- 采用**类型: 简述**的格式，类型包括：`feat` / `fix` / `refactor` / `docs` / `chore` / `style` / `perf` / `test`
- 正文应充分描述**做了什么、为什么做**，必要时说明影响范围
  - 不允许只有一行简述就提交，正文是必需的
  - 涉及多文件/多模块时，按模块分条列出变更内容
  - 使用 Markdown 语法，如无序列表
- 关联 Issue/PR 时在正文末尾标注（如 `Close #123`）
